# Full Code Review & Scrum Agenda (Sprint Planning)

In preparation for our next sprint, I've conducted a full code review across the repository, focusing on `src/`, `src/std/`, and `src/cartanc/`. Here are the discoveries, blocking issues, and read-ahead items for our upcoming sprint.

## 1. Discovery: Legacy vs. Active Compiler Files
There is a stark architectural split in the codebase right now:
* **The Prototypes (`src/*.car`)**: Files like `src/ast.car`, `src/llvm_codegen.car`, and `src/parser.car` represent an older, idealized prototype of the compiler. They utilize a cleaner, object-oriented design using `struct` and `trait` (e.g., `struct LLVMGenerator`, `trait AstNode`).
* **The Active Self-Hosted Compiler (`src/cartanc/*.car`)**: Files like `src/cartanc/llvm_codegen.car` and `src/cartanc/type_checker.car` are the ones currently bootstrapping the compiler. They use a much lower-level subset of Cartan (raw array trees, `tree_get`, and float discriminants) because they were likely generated via an early transpilation step or built before structs were fully working.

> [!TIP]
> **Action Item**: We need to decide the fate of `src/*.car`. We can either **archive/delete** them to prevent agent context confusion, or **port** their cleaner OOP architecture into `src/cartanc/` once `cartanc_stage2` is stable enough to compile structs. 

## 2. Discovery: Standard Library Audit (`src/std/`)
The standard library in `src/std/` contains robust foundational wrappers (`io.car`, `string.car`, `memory.car`, `net.car`). 
* I audited `string.car` and noticed it uses array indexing (e.g., `s[len]`). Unlike the abstract tree nodes in the compiler, this is perfectly safe and native for C-style strings/pointers in Cartan.
* We have placeholders like `ingest.car` for web scraping, and `memory.car` has a few hardcoded `malloc` sizes based on LLVM's `float` ABI.

## 3. BLOCKING ISSUE: The Great Discriminant Desync in `llvm_codegen.car`
During our AST audit, I discovered a critical "whack-a-mole" risk lurking in the self-hosted compiler.
* The `src/cartanc/type_checker.car` and `src/cartanc/parser.car` perfectly align with the new AST discriminants in `ast.ch` (e.g., `Expr::BinaryOp` = 16.0, `Stmt::ReturnStmt` = 24.0).
* However, **`src/cartanc/llvm_codegen.car` is using entirely outdated discriminants!** It expects `24.0` for `BinaryOp` and `114.0` for `ReturnStmt` (which appears to be mathematically shifted by `+64` for statements).
* **The Danger**: Even though `cartanc_stage2.exe` builds perfectly, the moment we use it to compile *any* actual Cartan code, `llvm_codegen.car` will fail to match almost every single AST node generated by the parser, resulting in silent failures or broken LLVM IR.

> [!CAUTION]
> **Blocking Issue**: If we do not align `llvm_codegen.car` discriminants with `ast.ch`, the self-hosted compiler will generate broken executables.
